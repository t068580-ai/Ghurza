# Ghurza (غرزة) — made-to-order tailoring

A two-sided marketplace built for the W4D2 systems-analysis exercise: customers describe a piece,
tailors bid **blind**, the customer pays a deposit through a payment provider, they chat once the
order exists, and the order closes with the balance, finished photos and a permanent review.

It is my own version of the system I reverse-engineered, not a copy of its screens.

- **The analysis this build starts from** (Parts 1–4 and the Systems Analysis):
  [docs/khiaty-systems-analysis.md](docs/khiaty-systems-analysis.md)
- **The design** (data model, every route and who may call it, the payment flow, OWASP mapping):
  [DESIGN.md](DESIGN.md)

**Stack:** Next.js 16 (App Router, Server Actions) · React 19 · Prisma 5 + SQLite · zod 4 ·
no auth or payment SaaS, so every security control is visible in this repo.

## How it works

```
Customer ──posts──▶ Request ──1:N──▶ Bid ──1:N──▶ BidRevision   (append-only history)
                                       │
               "Accept & pay" creates  ▼
               a PENDING Payment ──▶ mock provider ──signed callback──▶ settleVerifiedPayment()
                                                                         │ (one transaction)
                                                                         ▼
                         Order  ACCEPTED → IN_PROGRESS → READY → COMPLETED
                           ├─ Messages (chat exists only here)
                           ├─ OrderPhotos (portfolio once completed)
                           └─ Review (one, immutable) → tailor rating
```

- **One login, two roles.** The role is read from the database on every request and never changes
  after signup (a database trigger enforces this too).
- **Blind bidding.** A tailor's queries can only load their own bid. Competitors come back as a SQL
  `COUNT`/`MIN` aggregate, shown only as **fixed ranges** (e.g. "200–300 KWD", "1–2 weeks"), so no other
  tailor's name or exact numbers ever reach the browser.
- **Revisions add, never overwrite.** Each change appends a `BidRevision`. A declined bid can be
  revised, and that puts it back in front of the customer.
- **The order comes from the payment, not the click.** "Accept & pay" only creates a PENDING
  payment, priced on the server. The order is created only after an HMAC-signed provider callback
  is verified, in the same transaction that marks the payment PAID.
- **Chat, photos and reviews hang off the order.** They can't exist before money is committed.

## Security checks you can run yourself

| What to try | How | Expected |
|---|---|---|
| See another tailor's exact bid | As Khaled, open the bisht request, then View Source / Network → search for "Badria" or "155" | Not there. Only the bid count and ranges for lowest total and turnaround. |
| Open someone else's order | As Amal, change the id in `/orders/<id>` to one of Fajer's | "Not found", the same as an id that doesn't exist. |
| Revise someone else's bid | DevTools → change the hidden `bidId` in the revise form to another tailor's bid | "Not found." Nothing changes. |
| Mass assignment | DevTools → add `<input name="status" value="ACCEPTED">` to any form | "Invalid form submission." |
| Pay a different amount | Accept & pay sends only `bidId`. There is no amount field to edit. | The server prices it from the bid. |
| Forge "payment succeeded" | `curl -X POST localhost:3000/api/payments/callback -H "Content-Type: application/json" -H "x-provider-signature: t=1,v1=00…" -d "{...}"` | `401 invalid signature`, nothing changes. |
| Skip the payment | Visit `/payments/<id>?status=paid` | Read-only page; shows what the DB says. |
| Chat before paying | There's no chat URL until an order exists | Orders page explains it opens after the deposit. |
| Upload HTML as a photo | Rename an `.html` to `.png` and upload | Rejected: the server checks the bytes, not the name. |
| Leak your location in a photo | Upload a phone photo with GPS EXIF | Metadata is stripped before storage. |
| Bypass the app and write to the DB | `node scripts/check-triggers.mjs` | 11 illegal writes, all blocked by SQLite triggers. |
| Everything automated at once | `npm run test:security` | 22 checks: image stripping, rate-limit burst, mock-payment guard, ranges, triggers. |
| Vulnerable dependencies | `npm run audit:deps` | 0 vulnerabilities at the time of writing. |

## Independent security review: findings and fixes

After the build, a separate reviewer agent audited the code with fresh eyes, not anchored on
the original reasoning. It reported 8 findings. All were real and all are fixed:

| # | Severity | Finding | Fix | Verified by |
|---|---|---|---|---|
| 1 | High | Mock payments defaulted to **on**: a deploy that forgot the variable would let any customer "approve" their own payment. | Default is now off, and the app **refuses to start** with mock payments on in production. | `test:security` |
| 2 | Medium | The public payment webhook read the whole request body before checking its size, so a huge upload could exhaust memory. | 411/413 before reading; the stream is capped at 2 KB even if `Content-Length` lies. | 50 MB body refused in 14 ms |
| 3 | Medium | Login lockout could be beaten by firing many guesses **in parallel**: each passed the "blocked?" check before any failure was counted. | Every attempt is counted first with an atomic increment; a password-check concurrency cap protects the CPU. | 40 parallel attempts, exactly 5 allowed |
| 4 | Medium | Per-IP limits trusted the client-supplied (left-most) `X-Forwarded-For`, and signup used one shared key a stranger could exhaust for everyone. | Right-most hop only (added by the trusted proxy); signup limited per email after validation. | Code review |
| 5 | Medium | A tailor could open a second "sock puppet" account to cross the 2-competitor threshold and read a rival's **exact** lowest quote. | Competition is shown as ranges, never exact figures. | Payload check in browser |
| 6 | Medium | JPEG stripping kept everything after the first scan: appended motion-photo video, extra embedded images, trailing payloads. | Allowlist rebuild that walks every scan and cuts at end-of-image; PNG uses a chunk allowlist. | `test:security` + decode check |
| 7 | Low | A revision made right after a decline could record the wrong earlier status in the permanent history. | Status re-read inside the write-locked transaction. | Code review |
| 8 | Low | `npm run setup` would wipe whatever database it pointed at. | Setup and reset refuse to run with `NODE_ENV=production`. | Code review |

Two hardening notes from the review were also applied: HSTS in production, and per-user (not
per-order-id) chat rate limiting so the limits table can't be grown with made-up ids.

## OWASP audit (homework)

> Install the OWASP security audit skill from https://github.com/agamm/claude-code-owasp and run a
> full security audit on my project. List every vulnerability you find and what I should do to fix it.

The skill (commit `1ae29cb`) was installed into this project's `.claude/skills/` (gitignored) and
run with its own five-step workflow and report format.

| | Report | Screenshot |
|---|---|---|
| Before fixes | [docs/owasp-audit-1-before.md](docs/owasp-audit-1-before.md) | [png](docs/owasp-audit-1-before.png) |
| Re-check after fixes | [docs/owasp-audit-2-after.md](docs/owasp-audit-2-after.md) | [png](docs/owasp-audit-2-after.png) |
| Submission PDF (analysis + audit) | [docs/khiaty-systems-analysis.pdf](docs/khiaty-systems-analysis.pdf) | |

**First run:** 0 critical · 0 high · 3 medium · 4 low. The audit showed that two fixes from the
earlier review didn't fully hold.

**Fixed:**
- **Login lockout bypass at window rollover.** Before the fix, 24 of 40 requests got through. Now only the request that restarts the window passes as #1; the rest are re-counted, so 5 of 40 get through.
- **Blind-bid ranges were decodable to a 5 KWD window.** Bands now use fixed edges. The auditor's re-check found that the top band could still reveal a value at the price cap, and that is fixed too.
- **Missing `Cross-Origin-Opener-Policy`** header.
- **Partly fixed: login DoS.** Password hashing is now limited to 2 concurrent operations, so a flood no longer starves the thread pool. Per-client limits still need a reverse proxy.

New tests for every fix are in `npm run test:security` (25/25 pass). Each one fails on the old code.

**Still open:**
- Medium: login DoS without a proxy
- Low: signup reveals which emails are registered
- Low: the common-password list has only 15 entries
- Low: no password change or MFA
- Low: no CSP `script-src`. A nonce-based CSP is the natural next fix.
